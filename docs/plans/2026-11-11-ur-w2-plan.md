## What changes

`pass-report` gains one section, `## Planning misses`, printed once for the whole window after the
last repo section and before `## Notes`. It covers the same merged PRs as the repo sections, so
`--since` and `--repo` narrow it the same way. Nothing else in the output changes: no repo table
gains a row, and no `## Notes` line is added.

### What the report reads

The report reads each merged PR's body, which it already holds (M1).

The section starts at the first line that reads `## Planning misses`, with nothing else on the
line but trailing spaces or tabs. It ends at the next line that starts with `# ` or `## `, or at the end of
the body. A `### Planning misses` heading starts no section (M3).

A miss line is a line in the section that starts in column 1 and is one of these:

- A list item: the line opens with `-`, `*`, `+`, or a number followed by `.` or `)`, then a space.
- A line with no list marker that opens with one of the ten tags, in either written form below.

A line that starts with a space or a tab is never a miss line. That leaves out a wrapped
continuation and a nested item (M4). A list item whose whole text is `None` or `None.`, in any
letter case and with trailing spaces ignored, is not a miss line (M7). A paragraph line with no tag is not a miss line either, since
real sections use such lines for a lead-in, for `None.`, and for the page footer (M4).

The class of a miss line is its tag when its text, after the list marker if it has one, opens with
one of the ten tags. A tag is written `[mechanism]` or with a backtick on each side, and both forms
count on both kinds of miss line (M6). The ten are `[mechanism]`,
`[file-list]`, `[permission]`, `[design-gap]`, `[stale-fact]`, `[owner-call]`, `[no-answer]`,
`[conflict]`, `[estimate]`, and `[ambiguous]`, matched in lower case exactly. Every other miss line
is `untagged`. That includes a line that opens with a bracketed word outside the ten.

### What the report prints

When at least one miss line is counted, the section has this shape. The numbers below are the ones
the T1 fixture produces.

```
## Planning misses

Miss lines: 15, in 3 of 7 merged PRs.

| Class | Misses | Per 100 merged PRs |
|---|---|---|
| mechanism | 3 | 42.9 |
| file-list | 2 | 28.6 |
| permission | 1 | 14.3 |
| design-gap | 1 | 14.3 |
| stale-fact | 1 | 14.3 |
| owner-call | 1 | 14.3 |
| no-answer | 1 | 14.3 |
| conflict | 1 | 14.3 |
| estimate | 1 | 14.3 |
| ambiguous | 1 | 14.3 |
| untagged | 2 | 28.6 |
| Total | 15 | 214.3 |
```

The table always has these twelve rows in this order, a zero row included, so two reports line up.
In the `Miss lines:` line, the second number is the count of PRs with at least one miss line.
"Merged PRs" is the count of PRs the report listed for the window across the repos it reports. The
last column is the row's misses times 100 over that count, to one decimal as the script's `fmt`
gives it (M2). The approved design states its baseline in that unit: "The baseline per 100 merged
PRs is 33 misses in all" (design line 298).

When no miss line is counted, the section is the heading, a blank line, and `No miss lines in the
window.`, the same form a repo section takes with no data (M2). No table prints. The report takes
this branch before it divides, so a window with no merged PR prints the same line.

The module docstring and the `argparse` description say the report covers planning misses as well
as timing.

Out of scope: the repo tables, the `## Notes` lines, the `gh` calls and their cache, the rule text
in `pass-core` (W4 owns it), and `docs/STATUS.md`, whose one line on planning misses sits inside
the conductor's round-report block.
