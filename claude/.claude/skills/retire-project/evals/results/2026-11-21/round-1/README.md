# retire-project, round 1 (2026-11-21)

This round ran the four `retire-project` evaluations on Haiku, Sonnet, and Opus, each with the skill on and off, for 24 sessions. The skill fails by the rule. With the skill on, it loaded on all three in-scope queries for every model and met all 27 in-scope behaviors. It did not stay unloaded on the out-of-scope fourth query for Haiku: `4-haiku-on` found the skill's SKILL.md in its working directory with Glob and read it, so `loaded` is true. Sonnet and Opus kept it unloaded there. With the skill on, 29 of 30 behaviors were met.

## Queries met in full with the skill off

Case 1 on Opus: `1-opus-off` meets all three behaviors. It backs up before any delete, detaches the domain before deleting the Worker, and stops with the real ids before anything is deleted. For Opus, this query doesn't separate on from off. Haiku and Sonnet without the skill miss behavior 3.

Case 4 is met with the skill off on all three models. That is expected, since the query is out of scope and the skill never loads in an off session.

## Behaviors missed with the skill on

`4-haiku-on`, behavior 1: the session globbed its working directory, found `.claude/skills/retire-project/SKILL.md` in the evaluation scratch folder, and read it, so the skill loaded without `/retire-project`. The `disable-model-invocation` flag keeps the skill out of the model's own invocation, but it doesn't hide the file from a Read. The cause looks like the runner placing the skill file inside the session's working directory, not the skill's description.
